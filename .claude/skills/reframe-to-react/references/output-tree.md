# Output tree — what the engine emits, per target

Shape of the emitted file tree. Deterministic: same scene + same options → same tree byte-for-byte.

## Per-target layouts

### `target: "inline"` (Phase 1)

```
.reframe/exports/<slug>-react/
├── src/
│   ├── pages/
│   │   └── <slug>.tsx          — entry; imports + renders sections in order
│   ├── components/
│   │   └── sections/
│   │       ├── Nav.tsx         — extracted by semanticRole=nav
│   │       ├── Hero.tsx        — extracted by semanticRole=hero
│   │       ├── PricingGrid.tsx — etc.
│   │       └── Footer.tsx
│   └── styles/
│       └── tokens.css          — design tokens as CSS custom properties (if designSystem present)
```

Each section file contains:
- `import React from 'react';`
- One functional component with inline `style={{ ... }}` on every element
- Optional `<style>` tag for timeline / behavior CSS (same as single-file exporter)
- `export default <SectionName>;`

### `target: "css-modules"` (Phase 1)

Same structure, but each section emits a companion `.module.css`:

```
.reframe/exports/<slug>-react/
├── src/
│   ├── pages/<slug>.tsx
│   ├── components/sections/
│   │   ├── Nav.tsx             — imports styles from './Nav.module.css'
│   │   ├── Nav.module.css      — ← NEW (sibling)
│   │   ├── Hero.tsx
│   │   ├── Hero.module.css
│   │   └── ...
│   └── styles/tokens.css
```

Note: as of Phase 1, the engine returns CSS content alongside the component but the materializer doesn't yet split into separate `.module.css` files — the CSS is inlined into a comment block in the component. **This is an implementation gap** documented in [roadmap.md](roadmap.md); real split-file CSS modules land in Phase 1.1.

### `target: "tailwind"` (Phase 2 — scaffolded)

Falls back to inline tree for the actual components, PLUS emits a config sketch:

```
.reframe/exports/<slug>-react/
├── src/ (same as inline target)
├── tailwind.config.ts          — ← NEW — extend theme with brand tokens
└── styles/tokens.css           — kept as reference
```

The `tailwind.config.ts` has `theme.extend.colors` and `theme.extend.fontFamily` populated from the scene's DesignSystem. Merge it into your project's real Tailwind config.

**In Phase 2**, components will emit `className="..."` with brand-aware Tailwind classes (e.g. `bg-primary text-ivory`) instead of inline styles.

### `target: "styled-components"` (Phase 2 — scaffolded)

Currently falls back to inline with no extra scaffold. Phase 2 will emit:

```
src/components/sections/
├── Hero.tsx                    — imports from './Hero.styles.ts'
├── Hero.styles.ts              — ← NEW — styled-components with brand tokens
└── ...
```

## Entry page shape

The entry page imports every section and renders them in order. With css-modules or tokens, tokens.css is imported at top:

```tsx
import React from 'react';
import '../styles/tokens.css';
import Nav from '../components/sections/Nav';
import Hero from '../components/sections/Hero';
import PricingGrid from '../components/sections/PricingGrid';
import Footer from '../components/sections/Footer';

const Pricing: React.FC = () => {
  return (
    <>
      <Nav />
      <Hero />
      <PricingGrid />
      <Footer />
    </>
  );
};

export default Pricing;
```

Reads like a sitemap. The whole page structure visible in the entry file.

## Fallback: no semantic roles

If the source scene has no children with `semanticRole`, the extractor can't split intelligently. Two fallbacks:

**Sub-fallback 1:** children with ≥ 3 descendants → treated as sections, named by their `node.name` (Pascalized).

**Sub-fallback 2 (final):** no sections extracted → single-file fallback. The entry file contains the whole scene inline, with a comment header:

```tsx
// Auto-generated by reframe exportToReactTree (single-file fallback).
// No sections with semanticRole were found in the scene — the full
// tree is rendered inline here. Re-run with semanticRole set on
// top-level children to get a split file tree.

import React from 'react';
// ... full scene component ...
```

The user can fix this by setting `semanticRole` on top-level children via `reframe_edit` and re-exporting.

## Tokens file shape

`src/styles/tokens.css` emits CSS custom properties under `:root`:

```css
/* Reframe-generated design tokens — do not edit by hand. */

:root {
  --color-background: #0A2540;
  --color-primary: #635BFF;
  --color-accent: #635BFF;
  --color-text: #F6F9FC;
  --color-muted: #425466;
  --font-primary: 'Stripe Sans', sans-serif;
  --font-size-body: 16px;
  --font-size-h1: 48px;
  --radius-0: 0px;
  --radius-1: 4px;
  --radius-2: 12px;
  --radius-3: 999px;
}
```

Sections can reference these as `var(--color-primary)` in their inline styles (Phase 1 behavior preserves hardcoded values; Phase 2 will emit var references).

## Determinism guarantees

- **Section name order** matches source INode child order
- **Disambiguation** uses numeric suffix deterministically: if two sections would be named `Section`, they become `Section`, `Section2`
- **Slug** is derived the same way every time: `slugify(pageSlug)` with fixed rules
- **Paths use POSIX slashes** (`/`) in the file map; materializer converts to OS-specific separators only at write time
- **File iteration order in tokens.css** follows the DesignSystem's own map iteration, which is insertion-order for `Map` — stable across runs
